Template Analysis — kpaivision

The kpaivision application is a React-based, WebGPU-accelerated SmolVLM-500M vision-language app. Before architecting the golf app, we extract the patterns and modules worth reusing.

Input Pipeline

File upload or browser getUserMedia() webcam capture. Frame passed as an image bitmap to the HuggingFace transformer pipeline.

Reuse: Camera capture pattern, input state management, loading lifecycle hooks.

Model Loading Lifecycle

SmolVLMModelContext.jsx manages async model warm-up, error handling, and progress reporting via React context.

Reuse: Replace SmolVLM client with TF.js BlazePose/MoveNet loader using identical context pattern.

Safety / Monitoring Loop

SafetyLoop.js runs a continuous frame analysis loop with configurable interval. useSafetyLoop is a clean custom hook.

Reuse: Adapt as useSwingFrameLoop.js — drives continuous pose estimation during video playback.

State Architecture

React Context + custom hooks. TrackerStore.js manages presence-tracking state with thresholds and detection logic.

Reuse: Replace presence-tracking state with swing-phase state machine using the same pattern.

3.1 — Input & Camera Configuration

  • Video formats: .mp4, .mov, .webm, .heic-converted
  • Resolution target: 4K / 1080p; sample every 2nd frame for performance
  • Camera view selector: Face-On | Down-the-Line toggle stored in state
  • Orientation normalization: Auto-detect portrait vs landscape; rotate canvas if needed
  • Pro swing slot: Second video input for side-by-side comparison
  • Frame rate: Target 30 fps processing; degrade gracefully on low-end hardware

3.2 — Pose Estimation

  • Model: TF.js BlazePose (33 keypoints) primary; MoveNet Lightning fallback
  • Keypoints used: Hips (23/24), Shoulders (11/12), Wrists (15/16), Ankles (27/28), Nose (0)
  • Confidence threshold: Score ≥ 0.5 per keypoint; lower → interpolate from neighbors
  • Normalization: Map to [0,1] canvas space; mirror if down-the-line (right-handed golfer)
  • Sequence storage: Array of swingFrame objects, one per sampled frame
  • WebGPU acceleration: Use TF.js WebGPU backend when available; fallback to WASM

Metrics Engine Design

Swing Phase Detection — 6 Phases

AddressLow variance window
BackswingShoulder rotation ↑
TopMax shoulder rotation
DownswingVelocity reversal
ImpactLead wrist → ball-line
FinishLow variance settle
PhaseDetection AlgorithmFallback
Address Sliding window (n=5 frames): hip + shoulder angle σ < 5° First frame of sequence
Backswing start First frame after Address where shoulder angle deviates > 8° from baseline Frame after Address + 10
Top of Backswing argmax(shoulderAngle) within first 70% of frames Frame with max shoulder angle globally
Downswing First frame after Top where shoulderAngle decreasing AND hipAngle increasing faster Top + 3 frames
Impact Lead wrist x-coord closest to ball-line x (recorded at Address); OR wrist y-velocity sign change Frame at 50% of Top→Finish span
Finish Last low-variance window after Impact: hip + shoulder σ < 8° for n=3 frames Last frame of sequence

Core Metrics — Mathematical Definitions

MetricFormulaAddressTopImpactFinish
Hip Rotation atan2(LHIP.y - RHIP.y, LHIP.x - RHIP.x) × (180/π) ±5° 35–50° >80° 80–100°
Shoulder Rotation atan2(LSHO.y - RSHO.y, LSHO.x - RSHO.x) × (180/π) ±5° 70–100° varies 90–110°
X-Factor shoulderAngle − hipAngle — 20–40° maintain —
Spine Tilt atan2(PELVIS→CHEST) vs vertical 12–20° 12–20° maintain 0–10°
Wrist Hinge angle(forearm vector, hand vector) at lead wrist 0–10° 50–90° hands ahead —
Swing Tempo backswingFrames / downswingFrames — — — 3:1 ideal
Weight Shift (lead_ankle.x − trail_ankle.x) normalized: 0=trail, 1=lead 50/50 trail-heavy lead-heavy lead-heavy
SQI Weighted composite of 7 sub-scores (each 0–1), normalized to 0–100 Single session score

Swing Quality Index (SQI) — Weighting

const SQI_WEIGHTS = {
  hipRotation:     0.20,   // most critical — power source
  shoulderRotation:0.18,
  xFactor:         0.18,   // coil = distance
  spineTilt:       0.16,   // consistency + contact
  wristHinge:      0.14,
  tempo:           0.08,
  weightShift:     0.06,
};

function computeSQI(phaseMetrics) {
  let score = 0;
  for (const [key, weight] of Object.entries(SQI_WEIGHTS)) {
    score += weight * normalizeMetric(key, phaseMetrics[key]);
  }
  return Math.round(score * 100); // 0–100
}

Visualization Layer

1. Skeleton Overlay

Dual-skeleton canvas: Your swing in KP blue (#5BA3D9), Pro swing in gold (#D4A843). Both normalized to same canvas space.

  • Draw 17 body segments (limb pairs)
  • Circle markers at each of 33 keypoints
  • Opacity proportional to confidence score
  • Toggle: show/hide individual skeletons
  • Phase scrubber: step through frames with slider

2. Joint Delta Heatmap

Color-codes each joint by positional error vs pro reference. Green = within tolerance · Yellow = slight deviation · Red = significant mismatch.

  • Compute Euclidean distance per joint per phase
  • Map distance → HSL color (120° green → 0° red)
  • Render circles at joint positions with glow radius = error magnitude
  • Legend: distance in normalized units

3. Tempo Chart

Bar chart showing backswing duration vs downswing duration. Target ratio 3:1.

  • SVG/Canvas bar chart with KP color scheme
  • Backswing bar: KP accent blue
  • Downswing bar: KP gold
  • Target ratio line at 3:1 (dashed, muted)
  • Your ratio labeled in large type above chart

4. Weight Shift Indicator

Horizontal progress bar per phase showing lead-vs-trail weight distribution.

  • 6 bars (one per phase) stacked vertically
  • Left = trail side · Right = lead side
  • Ideal zone highlighted in muted green
  • Your position shown as animated dot

5. Club Path Approximation

Lead wrist trajectory from Top → Impact → Finish drawn on canvas as Bézier curve.

  • Sample wrist position at key phase frames
  • Draw smooth cubic Bézier through waypoints
  • Color gradient: blue (top) → gold (impact) → muted (finish)
  • Ideal path overlaid as dashed reference line

6. Swing Plane Lines

Computed swing plane overlaid on frame canvas — the line connecting wrists at Top through ball position.

  • Use lead shoulder → ball address line as reference plane
  • Draw on-plane (blue) vs off-plane (red) indicator
  • Show arm plane separately (trail arm angle at Top)

UI Shell — Tab Structure

Seven tabs, each styled with KnowingPath.ai glowmorphic cards, Inter typography, and the standard color palette.

Tab 1 — Swing Analyzer

Primary input interface. Dual video upload (you + pro). Camera view selector. Analysis trigger button. Real-time pose overlay during processing.

  • Video drop zone with dashed gold border
  • Face-On / Down-the-Line toggle (KP pill tabs)
  • Canvas overlay on video element
  • Progress bar during frame processing (KP blue glow)
  • Coaching cue banner appears after analysis

Tab 2 — Metrics

Phase-by-phase metrics comparison table. Your values vs Pro values vs Ideal range. 18 metric rows × 4 phases.

  • Phase selector tabs (Address / Top / Impact / Finish)
  • Table with color-coded diff column (green/yellow/red)
  • Hover on row → coaching cue tooltip
  • Export to CSV button

Tab 3 — Overlays

Interactive canvas with toggle controls for all 6 overlay types. Frame scrubber to step through swing.

  • Checkbox grid for overlay toggles
  • Phase jump buttons (snap to Address / Top / Impact / Finish)
  • Frame scrubber slider
  • Canvas zoom (1× / 1.5× / 2×)

Tab 4 — Scorecard

Swing Quality Index hero display. Sub-score breakdown per metric. Glowmorphic card with animated score ring.

  • Large SQI number (0–100) with animated circle progress
  • Letter grade (A+ through F) in gold/blue/red
  • 7 sub-score bars (one per SQI component)
  • Historical best / session average comparison

Tab 5 — Radar Chart

Hexagonal radar showing all 5 core metrics vs ideal ranges. Dual trace: Your swing (blue) / Pro (gold).

  • Canvas-based radar (no library dependency)
  • Axes: Hip / Shoulder / X-Factor / Spine / Wrist
  • Filled polygon for Your swing (semi-transparent blue)
  • Stroke-only polygon for Pro (gold)
  • Ideal zone ring (muted green fill)

Tab 6 — Trends

Line graph of SQI history over sessions. Individual metric trends. Streak counter.

  • SQI line chart (last 20 sessions)
  • Metric selector dropdown to swap displayed metric
  • Session date labels on x-axis
  • "Best Swing" callout card (gold border)
  • Streak: consecutive sessions above SQI threshold

Tab 7 — Settings

App configuration. Golfer profile. Data management. Model selection.

  • Golfer tag input (used in IndexedDB records)
  • Handedness toggle (right / left)
  • Pose model selector (BlazePose / MoveNet Lightning / MoveNet Thunder)
  • Frame sample rate slider (10–60 fps)
  • Clear session data button (with confirmation)
  • Export all data to JSON

Test Strategy

All tests run browser-locally (Vitest + jsdom, or native browser test runner). No server dependencies.

Unit Tests — MetricsEngine

  • Hip rotation: known keypoints → known angle ±0.1°
  • Shoulder rotation: symmetric vs asymmetric pose
  • X-Factor: zero at address, 30° at top (synthetic)
  • Spine tilt: perfectly upright → 0°; forward address → 15°
  • Wrist hinge: straight wrist → 0°; 90° hinge → 90°
  • Boundary: missing keypoints (score < 0.5) → NaN handled gracefully

Unit Tests — PhaseDetector

  • Perfectly still sequence → all phases = frame 0
  • Synthetic ideal swing sequence → correct phase boundaries
  • Short video (<20 frames) → graceful degradation
  • High-noise pose data → phase detection not corrupted
  • Left-handed golfer flag → phases still correct

Unit Tests — SQIEngine

  • All metrics in ideal range → SQI = 100
  • All metrics at worst boundary → SQI = 0
  • Missing metric → weighted score redistributed
  • SQI weights sum to 1.0 (assertion)
  • Correct coaching cue generated per metric deviation

Integration Tests — SwingDB

  • Save swing → retrieve by ID → data matches
  • Save 50 swings → list all → correct count
  • Delete swing → verify gone
  • Schema v1 → simulated v2 migration → data preserved
  • clearAll() → store empty
  • Large frame array (>500 frames) → save/retrieve without corruption

Stress Tests — FrameSampler

  • 600-frame video: processing completes <90s
  • No memory leak after 10 consecutive analyses
  • Cancel mid-analysis → state resets cleanly
  • 4K video → canvas resize → no keypoint drift

UI Rendering Tests

  • Tab navigation → correct panel shown each time
  • Radar chart renders without canvas errors
  • Scorecard ring animates 0→SQI value
  • MetricsTable: 18 rows rendered for complete analysis
  • CoachingCueBanner dismisses on click
  • Settings persist to localStorage across page reload

Risk Register

BlazePose fails to load (model CDN issue) Medium High Fallback to MoveNet Lightning; cache model to IndexedDB after first load
WebGPU not available in browser Medium Medium Detect at startup; graceful fallback to WASM backend; show performance warning
Phase detection fails on unusual swings Medium Medium Manual phase override UI (drag handles on frame scrubber); fallback heuristics documented
4K video too large for canvas memory Low High Downsample to 1080p before frame extraction; max canvas dimension = 1920px
IndexedDB quota exceeded (many large sessions) Low Medium Store frames as optional field; warn user at 80% quota; auto-prune oldest records
Poor pose confidence on baggy clothing Medium Medium Show keypoint confidence warning per joint; filter low-confidence frames from metrics

Issue #1 — Portrait Video Not Displaying

RESOLVED 2026-04-29

File: src/core/FrameSampler.js  ·  Full doc: updated_docs/WIP/problems-found/04292026-video-orientation-issue.md

Symptom

aom-side-swing.MOV (iPhone video) did not display in the <video> element after upload — preview stayed black. StacyLewis-Side-Swing.MOV loaded fine. Both are MOV/H.264 files with moov at file start.

Root Cause

Binary parsing of the QuickTime tkhd transformation matrix revealed a 90° CW rotation flag in the iPhone video (portrait recording). Chrome/Edge fires loadedmetadata but does not proactively decode the first frame for rotated files — the <video> element stays blank until a seek is issued.

Filetkhd RotationOrientation
aom-side-swing.MOV90° CWPortrait — iPhone vertical recording
StacyLewis-Side-Swing.MOV0° (identity)Landscape — normal horizontal recording

Fix — loadVideoFile() in FrameSampler.js

videoEl.addEventListener('loadedmetadata', () => {
  // Seek forces first-frame decode without awaiting seeked event
  // (seeked can silently not fire at t=0 — resolving on it hangs the Promise)
  videoEl.currentTime = 0.001;
  resolve();
}, { once: true });
// Also fixed: error handler now uses videoEl.error.message (not e.message)

Reference Copy — aom-new-side-swing.mov

A clean H.264 browser-compatible copy was produced with ffmpeg. Two failed attempts first:

  • Fail 1 — OpenCV mp4v: Produced 83 MB MPEG-4 Part 2 file — Chrome/Edge does not support this codec
  • Fail 2 — ffmpeg transpose=1: Double rotation — ffmpeg's -autorotate is ON by default, so the video was already correct before transpose=1 rotated it a second time (head east, feet west)
  • Success — ffmpeg without transpose: Let auto-rotate bake the orientation, strip all metadata with -map_metadata -1, add -movflags +faststart
ffmpeg -y -i aom-side-swing.MOV -c:v libx264 -preset fast -crf 23 \
  -c:a aac -movflags +faststart -map_metadata -1 aom-new-side-swing.mov
# Result: 5.5 MB · H.264 · 328 frames · no rotation metadata · moov at front

Action Items

  • Add portrait warning banner in handleFileSelect (app.js) when videoEl.videoHeight > videoEl.videoWidth
  • Add landscape orientation guidance to upload hint text in index.html
  • Re-record aom-side-swing.MOV in landscape mode for accurate pose estimation
  • Add video orientation validation to loadVideoFile pipeline

Recording Requirements

  • Both videos must be landscape (horizontal) — phone held sideways
  • Same camera angle for both (face-on or down-the-line)
  • Same approximate distance from the golfer
  • Portrait videos can be corrected: ffmpeg -i in.MOV -c:v libx264 -crf 23 -c:a aac -movflags +faststart -map_metadata -1 out.mov

Public vs. Private Repository Sharing Strategy

SwingKrazy repository is currently PUBLIC. This document explains the implications and when you might consider changing to private, along with how access works in each scenario.

✅ Current Status: PUBLIC Repository

The repo at github.com/KnowingPath-ai/swingkrazy is public, allowing anyone to:

  • Clone the repository directly without authentication
  • Download sample videos (raw-videos/CV-golf-analysis/pro and amateur)
  • View all source code
  • Access via any of three methods: CLI, GitHub Desktop, or ZIP download

Recommendation: Keep PUBLIC for sample library distribution. Users can access immediately without friction.

📋 Decision Summary

Keep SwingKrazy Repository PUBLIC for the following reasons:

  • Sample Video Distribution: Users can access pro and amateur reference swings immediately without friction
  • Zero Authentication Friction: No need to manage GitHub collaborators or send invites

  • Open Source Philosophy: Aligns with sharing a free, helpful tool with the golf community
  • Netlify Users: Can clone directly without any setup or credentials

When to Consider Private: Only if you plan to charge for the app or restrict access to specific users (future paid tier). Then provide private credentials to paying customers.
